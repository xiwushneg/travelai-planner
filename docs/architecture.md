# TravelAI 工程架构

## 1. 定位

这是一个不依赖外部 LLM 即可运行的**完整 Web 旅行规划工作台**。当前版本增加本地目录导入和可替换路线估算器，但仍遵守同一条正确性边界：确定性算法负责约束与排程，本地检索负责提供带来源的证据，外部地图只负责通勤估算；模型或地图服务都不能绕过时间、版本和证据规则。

## 2. 运行拓扑

```text
Browser (SPA)
  │ 同源 HTTPS / HTTP
  ▼
FastAPI ──静态挂载──> frontend/dist（Vite 已编译 JS/CSS）
  │
  ├─ Web/API DTO 与异常映射
  ├─ PlanningService
  │    ├─ Repository（每次规划读取最新 SQLite 目录）
  │    ├─ EvidenceRetriever（演示/自定义攻略 + 数据库导入攻略）
  │    ├─ 确定性 Scheduler
  │    │    └─ RouteEstimator（单次规划缓存、限次、降级）
  │    │         └─ Local / Mock / Baidu DirectionLite
  │    ├─ 不可变版本写入与 optimistic lock
  │    └─ 局部修改 + 版本 diff + 运行记录
  └─ SPA fallback（仅页面路由）

运维命令行
  └─ scripts/import_data.py
       ├─ JSONL / CSV 解析与逐行错误定位
       ├─ Pydantic 严格校验、重复 ID 检查
       ├─ dry-run（不创建/修改数据库）
       └─ 单事务幂等 upsert + JSON 报告
```

前端不保存主数据、不直接连接 SQLite，也不接收百度 AK。刷新页面后通过最近行程列表恢复服务端版本。

## 3. 核心正确性边界

1. **确定性优先**：开放时间、闭馆日、停留时长、通勤缓冲、人数票价、预算与最大点数都由确定性代码检查。
2. **搜索不丢必选项**：动态规划在每天的景点子集上搜索，先满足全部必选，再优化普通候选。
3. **目标日全量替换**：`modify-day` 对目标日去重、跨日冲突和可达性进行校验，其他日期默认作为不可变边界。
4. **版本不可变**：已保存版本是历史快照；后续目录更新不会回写旧版本。新版本必须基于 `expected_version` 创建。
5. **来源而非事实幻觉**：所有景点和攻略携带来源状态、URL（如有）、最后核验日期与备注。`verified` 导入仅表示字段完整，仍需用户实际核验。
6. **地图可替换、可降级**：本地估算沿用 Haversine；百度仅返回一次路线估算，不冒充实时路况。失败、缺 AK 或超出单次限次时回退本地并保留警告。
7. **导入不绕过校验**：未知字段、缺失必填字段、错误坐标/日期/票价、同文件重复 ID 都会使整批预检失败。

## 4. 排程算法

### 状态

`SearchState = (day_number, remaining_spots)`。每个状态缓存最优的“当前及后续日期”方案，减少重复子问题。

### 单日子问题

对当日候选子集枚举排列，使用可行性剪枝：

- 当前时间 + 通勤 + 停留不能超过关闭时间；
- 必须满足营业日期与闭馆日；
- 固定午餐作为时间锚点，不能跨过午餐；
- 当日结束后，最后一个景点到下一固定时间点的通勤仍需可行；
- 保留通勤估算最小的方案。

### 全局优化

每天允许放置普通候选的任意子集，也允许空日；必选景点不可被放弃。跨天动态规划比较通勤估算、总费用与未排入数量。搜索节点达到上限会返回冲突说明，不会把普通候选静默当作已排入。

## 5. 路线估算与地图适配

`RouteEstimator` 在每次创建或修改行程时新建，按坐标与交通参数缓存去重：

- `LocalRouteProvider`：球面距离 ÷ 平均速度 + 缓冲，默认且完全离线。
- `MockRouteProvider`：固定结果的离线测试替身。
- `BaiduRouteProvider`：服务端请求 DirectionLite，使用 WGS84 坐标，读取首条路线距离与时长；全局 `BAIDU_ROUTE_MODE` 决定 walking/driving/transit 服务。

在线估算器记录单次规划的在线调用次数。缓存命中不重复请求；超过上限、请求异常或返回结构异常时使用本地结果。通勤段保存 `basis`、`provider`、`is_online`，行程警告说明降级。健康检查只暴露地图模式，不暴露 AK。

## 6. 本地目录导入与证据

景点与攻略分别存于 SQLite 的 `spots`、`guides` 表，完整模型 JSON 加城市索引。导入器先读取并校验完整文件，只有全部通过才打开数据库写事务；因此格式错误或 dry-run 不会创建数据库。

后续规划直接读取最新景点。证据检索把应用启动时提供的演示/自定义攻略与数据库攻略按 ID 合并，数据库同 ID 项优先。每个历史行程仍保存当时的证据快照。

## 7. 局部修改与版本比较

```text
请求 trip_id + expected_version + day_number + desired_spot_ids
  → 读取当前版本并检查 optimistic lock
  → 检查目标日 ID 重复、与其他日期重复、未知景点
  → 其余日期转为 locked_days
  → 目标日使用最新目录重排
  → 原子写入 version + 1
  → 计算结构化 diff
  → 更新 AgentRun
```

景点实际变更、目标日顺序变化、时间/费用变化和日程内移动都会体现在 diff。被锁定的其他日期内容逐项复用，并单独校验。

## 8. 异常与运行记录

- 不可行请求：422 `PLANNING_INFEASIBLE`，包含冲突与 `run_id`，不保存假行程版本。
- 过期版本：409 `VERSION_CONFLICT`，返回当前版本，不覆盖他人修改。
- 不存在的行程/版本/运行：404。
- 非法局部修改：400。
- 每次创建/修改/重试均留下请求、状态、错误、关联版本与结果摘要；数据库错误不会伪装成规划成功。

## 9. 已知边界与下一阶段

- 本版本没有登录、多租户、支付、在线预订、对象存储或多副本调度；公网部署前必须补充认证授权、限流、审计与备份。
- 没有浏览器上传控制台；数据导入通过后端 CLI 完成。
- 检索仍是本地词项匹配，不是向量数据库。需要语义召回时可替换 `EvidenceRetriever`，但不能删除来源与核验状态。
- 全局搜索有节点上限；大型多日多景点目录需要更高级的约束求解、缓存和任务队列。
- 百度真实服务需要用户自己的 AK、权限与配额；本交付只用本地模拟响应验证请求/解析，不声称已验证真实公网接口。
- 目前仍是单用户信任模型；个人任务清单保存在浏览器本地，不能视为服务端行程数据。

## 10. 架构验收

1. 同一输入重复运行产生相同的核心排程，版本号与存储副作用除外。
2. 必选景点、开放时间、午餐、预算与锁定日均不能被优化过程绕过。
3. 任一非法导入记录使整批不写库；重复合法导入保持幂等。
4. 无 AK、地图失败和在线限次均可离线降级，且通勤来源可检查。
5. 原核心排程、局部修改、乐观锁、版本 diff、Web/API 回归全部通过。
